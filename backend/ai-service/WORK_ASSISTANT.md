# Personal work assistant — phase 1

The private assistant is available on Dashboard, Projects (list/detail) and Calendar. It is separate from channel/DM `@ai`, which still cannot query task assignments.

## Behavior
- Multiple private server-side conversations per personal/project scope. Users can create a new conversation and reopen previous ones from the scoped, paginated history list. The first question is the title; inaccessible project content is hidden. Earlier conversations remain intact.
- Default project audience is “Việc của tôi”; authorized users can switch to “Toàn project”.
- Today refreshes on opening and every minute. Each question reads fresh source data.
- Suggestions cover urgency, blockers, task descriptions/checklists/subtasks, personal focus history and 7/30-day progress.
- Explicit comparisons of 7 and 30 days load both exact metric windows. Source failures remain distinct per period, and permissions for both snapshots are rechecked before saving.
- Conversation-list cursors are opaque tokens containing an ID and a frozen activity timestamp with PostgreSQL microsecond precision. Pass nextCursor back unchanged; message-history cursors remain UUIDs. Older UUID conversation cursors remain accepted for compatibility.
- Scheduling uses fresh Calendar busy intervals and the account time zone (Calendar time zone as fallback). No manual work-hour preferences, form or API are used.
- Calendar gaps cover the next seven days, exclude past time and busy/all-day events, and require complete Calendar data. A gap means no recorded event, not confirmed working hours or availability. The model offers tentative daytime suggestions unless the user requests other times; it does not invent fixed workdays or lunch breaks.
- Task links are generated by the server. No task/calendar/checklist writes, comments or attachment-content reads are exposed.
- Calendar exports private task information plus busy intervals; event titles/descriptions, Pomodoro notes and other users’ focus data are not exported.

## Setup
From the repository root:

```powershell
node backend/scripts/configure-work-assistant.mjs
cd backend/ai-service
npm run build
npm run migrate
```

The setup script synchronizes a dedicated `WORK_ASSISTANT_SERVICE_KEY` in the three local service env files without printing it. Existing unrelated settings remain intact. AI still requires its existing `AI_ENABLED=true`, gateway keys, model configuration, PostgreSQL and quota infrastructure.

Build/restart AI, Project and Calendar services after configuring them. Existing Kong `/api/ai` routing covers the public endpoints.

For containers, set AI `WORK_ASSISTANT_PROJECT_URL` and `WORK_ASSISTANT_CALENDAR_URL` to the corresponding internal service URLs instead of localhost. Disable only this feature with `WORK_ASSISTANT_ENABLED=false`.

Migration 003 is additive and idempotent. It creates only AI-owned sessions, messages, request admission records and preferences. It does not alter task schemas. Migration 004 adds the conversation activity timestamp and list index without removing existing histories. There is no history-delete API or UI action.

## APIs
All public routes use the existing authenticated gateway guard under `/api/ai/work-assistant`.

| Method/path | Purpose |
| --- | --- |
| GET /overview | Today context; optional projectId, audience and account timeZone |
| GET /session | Latest conversation or explicit sessionId; optional projectId and before message cursor |
| GET /sessions | Private conversation list in a personal/project scope; optional before conversation cursor |
| POST /sessions | Create a separate conversation; optional projectId |
| POST /sessions/:id/messages | question, requestId, audience, optional account timeZone; SSE |
| POST /requests/:id/cancel | Cancel this user’s request |

SSE emits request, status, done or error, plus heartbeat comments. Done contains the persisted answer, scope, source states, data timestamp and server-created task references. Each stored answer retains its data timestamp and audience. A terminated stream never silently becomes a successful answer.

Project and Calendar expose secret-authenticated, read-only `POST /internal/work-assistant/context`. Project also exposes `POST /internal/work-assistant/authorize`. The AI service derives user identity from the gateway, never from client/model arguments; the source services enforce ownership/membership against their own databases.

Project sessions require current read access. Personal messages that reference a revoked project are redacted on history reads. Access is checked again before saving an answer.

## Metrics and limits
- Aggregates cover all matching authorized tasks, independently of capped model details.
- Project context reads at most 60 unfinished task details; model prompts use at most 35 within a 20 KB context budget, with explicit partial-detail flags.
- Completed tasks without a deadline are excluded from the on-time percentage. Comparisons use the currently stored deadline; historical deadline changes are unavailable.
- Calendar TASK records belong to personal calendars; project task copies are excluded.
- Busy intervals are capped at 2,000. Incomplete recurrence materialization or busy pagination disables concrete free-slot suggestions.
- The model can request only a 7- or 30-day context, with at most three model turns, existing model quotas, one active request per user, eight requests per minute and a 105-second request deadline.
- Difficulty and duration are estimates from available task/focus data, not newly stored task fields.

## Verification
- AI: `npm run build`, then `node --test test/work-assistant.test.cjs test/conversation-agent.test.cjs test/conversation-worker.test.cjs test/modules.test.cjs test/auth.test.cjs`.
- Project/Calendar: run their Jest work-assistant specs, TypeScript build checks and ESLint on the new modules.
- Frontend: `npm run typecheck`, `node --test scripts/work-assistant.test.mjs`, focused ESLint and `npm run build -- --webpack`.
- Browser checks use fixture data to verify lazy loading, timezone, Calendar-derived gaps, SSE, reload, new/reopened conversations, scope, mobile modality and permission revocation. They do not evaluate a live model’s planning quality.

Local integration note: PostgreSQL on port 5433 and Docker were unavailable during implementation, so the migration has been verified in an isolated PostgreSQL-compatible database but has not been applied to the local application database. Run the setup/migration commands once infrastructure is available.
